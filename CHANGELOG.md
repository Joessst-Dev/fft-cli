# fft

## 0.11.0

### Minor Changes

- 7d78a0b: `fft auth token --refresh` mints a new id token first and prints that one, so a token you hand to a CI job, a sandbox or a long-running script has its full lifetime instead of whatever was left of the cached one (as little as five minutes). It replaces `fft auth refresh && fft auth token`, exits 4 when neither the refresh token nor the stored password works and 2 for a fixed `FFT_ID_TOKEN`, and reports how long the new token is valid on stderr; stdout is still just the token. `fft auth token --help` now says when the cached token may be close to expiry.
- cb69c38: Generated list commands that page with `startAfterId` (for example `fft category get-categories`) now take `--all` and `--max-items`, with the same bound and the same warning on stderr when a list is cut short. `--size` is now checked against the maximum the API declares, so `--size 250` on a list capped at 100 fails with a usage error instead of an HTTP 400 — including through `fft api`.
- cd06280: `FFT_ID_TOKEN` now works on its own in headless mode: set `FFT_BASE_URL` and `FFT_ID_TOKEN` and fft runs from the environment, without the `FFT_FIREBASE_API_KEY` and `FFT_EMAIL` placeholders it used to demand. The password path is unchanged and still needs the base URL, the Firebase key and an email together.
- afb68ca: New `fft network check` finds routing gaps in a snapshot taken with `fft network snapshot`, offline and without sending a request. It reports five rules: `no-source` (a store no online source reaches for some kind of order), `peer-coverage` (a store no hub or supplier reaches although one reaches at least 90% of the stores in its country), `dangling-ref` (a target, exclusion or context value that names nothing), `offline-ref` (an offline facility that connections still lead to) and `duplicate-edge`. The kinds of order are the tag combinations of recently routed orders, and the hubs are the facilities whose connections reach far more facilities than anyone else's. Both are printed on stderr, along with each country's hub and supplier coverage. Findings go to stdout, as a table or with `-o json` including each one's evidence and next step. `--rule` runs a subset and `--snapshot` names a file. The new exit code 11 means the check ran and found problems; a check that could not run exits with that failure's own code.
- 56e0273: `fft network check` now follows a committed `fft-network.yaml`. `fft network infer` writes a starter one from a snapshot, every value with the reason it was chosen. It pins the hubs, the peer grouping and where the kinds of order come from, and adds one expectation per country a hub already covers. With a config, `check` adds three rules. `expect` reports a store fewer hubs, stores or suppliers reach than the file asks, optionally within `maxTransitDays`. `config-drift` reports a pinned hub the network no longer treats as one, a hub it does not pin, or a routed kind of order the declared ones miss. `suppress` entries accept a finding until a date, with a reason: suppressed findings are counted on stderr, and an expired suppression suppresses nothing and is warned about. `check` reads `./fft-network.yaml` when it exists, and exits 3 for a file it cannot use or one named with `--config` that is not there. `fft network config validate` lists every problem in the file with its line, including expired suppressions and anything it names that the snapshot does not have. `fft network config schema` prints the file's JSON Schema.
- c0e68db: New `fft network reach --to <facility> [--tag id=value]` shows, from a snapshot, every connection that could lead to a facility for a kind of order, whether it applies, and the first exclusion or context entry that rules it out. stderr names the reason that excludes the most connections. New `fft routing strategy tree [<id>]` draws a routing strategy (the one in use by default) as the tree the router walks, with each node's fences and ratings, inactive branches folded (`--all` unfolds them). `--order <id>` marks the branch the router took for that order from its latest decision log. `fft network check` gains rules for the strategy in use: `strategy-in-use`, `strategy-category`, `strategy-inactive`, `strategy-expired`, `strategy-fallback`, `strategy-no-rating` (a path whose merged config has no active rating) and `toolkit-hardcoded-id` (a facility id in a toolkit rule, compared or inside a JSONPath filter, that names no facility). `fft network snapshot` now also reads the routing node config categories.
- dfd25dc: New `fft network snapshot` reads a whole fulfillment network into a local file: every facility, every facility's connections, the facility groups, tags and routing strategies, and the most recent routing decision logs with the tags of the orders they routed. It is the first piece of `fft network`, the offline toolkit for finding routing gaps (#336). Every request is a read, so it runs under `--read-only`. A large network takes an hour or more, so the crawl allows itself 4h unless you set `--timeout`, reads `--concurrency` facilities at a time, backs off when a gateway throttles, and when it stops (an expired session, Ctrl-C) `--resume` continues where it left off. The snapshot goes to the cache directory, readable by you only; stdout carries a summary, and progress goes to stderr. Cursor searches (`fft facility list --all` and the other list and search commands) now retry a page that hit a 502 or a dropped connection, as GETs always have: a search changes nothing, so sending it again is safe.
- b8436fe: Network failures and timeouts now exit 9 (upstream unavailable) instead of 1, so scripts can retry them: a refused or reset connection, a DNS or TLS failure, a proxy that is down (a 5xx on `CONNECT`), and `--timeout` expiring. The message still names the URL. Ctrl-C still exits 130, and a proxy refusing with 403 or 407 still exits 1, because retrying will not change it.

### Patch Changes

- ea502c5: The agent skill (`fft skill`) and the docs site now cover finding routing gaps. A new network reference walks through the workflow: snapshot, check, explain a finding with `reach` and `routing strategy tree`, then pin decisions in `fft-network.yaml`. It covers every rule, the config file and gating CI on `fft network check`. It tells an agent to report findings and to propose a suppression, never add one. The CI guide gains a section on gating a job on exit 11.
- ea54523: `fft order search` now explains the API's "Query too complex" error. On a tenant with a very large order history the API rejects `--since`/`--until` and `--sort`, and shrinking `--size` does not help; fft now points to narrower filters (`--tenant-order-id`) and `fft routing decision-logs` (which in practice lists the newest routings first; the API does not guarantee an order). The exit code is unchanged, and `--help` documents the limit.
- 6de1e2d: A refusal from a proxy, firewall or gateway between fft and the tenant is now reported as such, instead of sending you to `fft auth whoami`. That covers a TLS-intercepting proxy that answers a 401, 403 or 407 inside the tunnel (with the proxy's own message), and an `HTTPS_PROXY` proxy that refuses to open the tunnel at all, which used to print only `Forbidden` or `Proxy Authentication Required`. Exit codes are unchanged.
- 7dab170: `fft routing decision-logs --all` no longer fails with a confusing `HTTP 404: Invalid ObjectId string` on the second page. The API cannot page this list past its first page, so `--all` now reads one page of up to 250 logs and warns on stderr when there are more, telling you to narrow the search with a filter.
- 7a17d4f: Every search now explains the API's "Query too complex" error, not only `fft order search`. On a tenant with a very large collection the API refuses a filter or a sort with HTTP 400, and its own advice (reduce the result set size) does not help: fft now says that a smaller `--size` will not help and to narrow the query with an exact-match filter, dropping any date range and the sort. This covers the curated `list` and `search` commands (with a sharper hint for `stock list`, `listing list` and `facility list`), every generated `search-*` command and `fft api search<Entity>`. An `--all` walk that is refused part-way now says how many pages and items it had read, and `fft network snapshot` stops at once instead of pausing and retrying. The exit code is unchanged.
- de55da8: `--all` list commands now say what happened when `--timeout` runs out mid-walk: the error names `--timeout`, how many pages and items were fetched, and suggests raising it, instead of a bare "context deadline exceeded". `--timeout` bounds the whole command, so large tenants need a larger value; the `--all` help now says so.
